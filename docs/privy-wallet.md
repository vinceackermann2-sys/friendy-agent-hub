# Belna Wallet with Privy

New Belna Wallets use a user-owned Ethereum wallet with USDC on Base (chain 8453).
Whop is retained only for access to previous balances and reconciliation of
previous card payments. The migration does not move or delete existing funds.
Subscription billing and purchases using existing payment methods remain separate.
Cards keep the **Apply interest** waitlist; this implementation does not issue cards.

## Ownership and agent authorization

Belna keeps its Supabase login. Wallet connection uses a Belna-owned email-code
dialog backed by the headless `useLoginWithEmail` hook on the current plan. There
is no separate Privy login page or user-facing Privy account signup. Privy retains
an internal user record for wallet ownership. Email codes stay in the owner form,
never in chat, storage or analytics. Registration and every authorization require a Privy-signed
identity token whose verified email matches the owner's confirmed Supabase email.
The backend also verifies embedded-wallet membership, wallet address, and the
wallet's owner quorum. The quorum must contain only that user, with no additional
authorization keys, nested quorum, delegated signers or wallet automations.

The model can read a balance and prepare an exact send or owner-requested Earn
action. An agent approval produces an `awaiting_owner` request, never a payment.
The owner reviews that request in Wallet and authorizes precisely its provider
URL, body, app ID, expiry and idempotency key with the Privy client SDK. The server
rebuilds the request from its durable record. It never receives wallet signing
keys, and the model never receives JWTs, signatures or provider secrets.

The database serializes requests per owner, enforces the $50 rolling app
allowance, and prevents a second action while one is unresolved. A timeout keeps
the reservation. Retries use the original idempotency key; unresolved requests
older than 23 hours require provider reconciliation instead of re-submission.
Pause and allowance controls apply to requests through Belna, not to direct use
of the user's keys. This is intentionally not an autonomous delegated wallet.

## Production activation

### Local preview

Run `npm run preview:wallet` and open `http://localhost:8000/app`. Sign in with
your existing Belna account. The preview forces its OAuth origin to localhost;
Google's OAuth client must allow `http://localhost:8000/api/auth/google/callback`
before Google login can return here. Email/password and email-code login work
without that Google callback registration. Add the app secret on line 4 of `.env.wallet.local`
and save; the preview restarts automatically. This ignored file is private and
never served as app content. The preview listens on loopback only and does not
poll production's scheduled tasks, automations or VM sweeper. Interactive chat
and owner-scoped task advancement remain available.

On October 8, 2026, the owner approved adding `http://localhost:8000` to the
production Privy allowed origins for testing. Both `https://belna.se` and the
local preview origin are allowed. Remove the local origin once testing is done.

This preview uses real accounts and provider infrastructure, not a demo balance.
The owner chooses their country before email verification and wallet creation.
The selected country is retained during background refreshes and saved with the
wallet. The owner must perform any actual registration, funding and money movement.
Earn is connected to the owner-created Aave USDC vault on Base. A new app
secret must be generated by the human in Privy's Basics → API keys page; never
paste it into chat or a customer wallet form.

After privately adding the existing or newly generated secret, run
`node scripts/configure-privy-wallet.cjs`. It verifies the credential with a
read-only Privy request, saves the configuration using the existing service-only
`put_server_secret` RPC, and confirms the saved value without printing it. Both
Express and the Lovable backend can read that shared Vault configuration. Restart
the backend after installation because configuration is cached for its lifetime.
Lovable's secure secret settings can also supply `PRIVY_APP_SECRET` directly to
its server runtime; never enter a credential in a Lovable chat message.

## Funding, withdrawals and Earn

Funding uses the fiat-only Deposit modal, restricted to EUR and USD, with Base USDC as the destination. Stripe quotes determine supported cards and payment methods. SEK needs Meld KYB approval, so it is not offered. Crypto deposit and exchange funding are not offered. Provider country coverage, KYC, fees and limits govern actual availability. Wallet balances and incoming USDC activity use live provider/onchain reads.

Belna displays the digital-dollar balance as USD and calls the lending product Earn. The underlying USDC asset, vault and signing checks keep their provider identifiers. A short digital-dollar disclosure remains beside the balance; provider checkout screens may identify the underlying token. Settings omit the receive-address row and label the controls 24-hour transfer limit and Pause wallet transfers, with explanations matching the rolling limit and pause behavior.

The action row is Add money, Send, Withdraw and Earn. Send accepts Belna email. Withdraw is a native Bridge bank payout: the owner accepts hosted Bridge terms, completes hosted KYC with the SEPA endorsement, links their own EUR-capable IBAN/BIC, and authorizes the exact USDC amount and immutable provider bank account ID. Verification is checked again before every payout. Bank deposits receive EUR; Swedish banks may charge EUR/SEK conversion. No FX amount or bank delivery time is guaranteed. Full IBANs are forwarded to Bridge after explicit owner consent and never stored in intents, chat or browser storage. Only provider bank IDs and masked destination labels are retained.

The agent can read masked bank references and prepare an exact owner-requested withdrawal after chat approval. It has no KYC or bank registration tool and no signing authority. A payout remains processing until fiat settlement succeeds. A failed bank action after crypto submission retains its reservation for provider reconciliation and is never automatically reissued. Legacy crypto withdrawal requests remain explicitly identified as wallet transfers.

Bank migration `20261008203000_privy_bank_withdrawals.sql` was applied atomically to `alikzitdkdiatimjygdz` and recorded in migration history on October 8, 2026. Existing owner RLS and rolling limits cover bank payouts.

Earn uses Aave USDC on Base, vault `jafrszfiu1t5dgr62x3rmvq2`, created by the owner on October 8. The configured performance fee is 10% of generated yield; users retain 90%. The vault and chain/token/decimals were verified through the live API before installation in the private Vault. Net user APY comes from `user_apy` basis points, converted to percent; no fixed rate is invented. Positions and realized/unrealized earned yield use the provider’s raw 6-decimal asset amounts. Withdrawals cannot exceed the available Earn position. Each operation requires owner authorization and risk acceptance. Yield can vary or be negative, and liquidity can delay withdrawals.

Base gas sponsorship is enabled for server-authorized wallet actions. The dashboard had $0 prepaid credits during verification. The owner must complete the credit purchase to support users with no ETH balance. Credit purchase, hosted KYC, account linking and real financial verification remain human actions. No actual funding, Earn deposit or bank payout was executed by the agent.

## Regulatory boundary

This architecture reduces app-held signing authority. It does not determine
regulatory status or guarantee that Belna is outside MiCA or other rules.
Finansinspektionen lists custody, exchange, execution/reception of orders and
transfers on behalf of clients as crypto-asset services. Product operation,
delegation, geographic reach, partner roles and Earn distribution need an actual
Swedish/EU regulatory assessment before launch. Switching providers alone is not
an exemption. No claim of exemption should be shown to customers.

## Verification

`npm run test:privy-wallet` exercises owner isolation, signer/quorum rejection,
agent requests, owner authorization, request tampering, timeout retries, expiry,
Earn risk checks, RLS, rolling limits, pause and account deletion. Wallet UI tests
use provider fixtures and do not perform financial transactions.

`node scripts/sync-lingon.mjs` builds the lazy browser SDK and generates the ESM
provider/store/routes for Lovable. Both Express and the edge API use the same
implementation. The SDK warms when an existing owner opens Wallet, without
sending an email code or opening authentication. Add money resolves its
destination from the authenticated owner's SDK wallet, avoiding a second full
snapshot. Independent balance, Earn, intent and activity reads overlap;
balances and ownership are still verified live before every transfer. No
balance or signing decision is cached to improve loading speed.

Belna's funding picker and money dialogs share the Belna wordmark, neutral
palette, rounded card, fields and buttons. Funding branding is added inside
the provider modal without replacing its method selection, checkout, terms or
owner confirmations. Hosted payment and identity providers retain their own
legal identity. The bank verification button opens the returned hosted link
in a new tab, with a visible fallback if popups are blocked. Checking status
keeps an unfinished link available. Local hosted KYC returns to the approved
localhost preview; other environments return to Belna's production app.

Validation on October 8, 2026: production build, wallet/regression suite, Privy
provider + SQL + client review + desktop/mobile UI suite, TypeScript SDK entry,
chat/approval cards, agent workflow and existing security boundary checks passed.
The real browser bridge with a fixture SDK also passed headless login checks on
desktop and mobile: failed delivery, invalid codes, resend, cancellation, session
refresh, owner switching and reuse of an already connected owner.
Production SQL verifies RLS on all three new tables, no anonymous access, no
authenticated writes, owner-only read policies and service-only reservation RPC.
Live owner wallet creation was confirmed by the owner. Live vault/position and Bridge status/account reads are verified separately. Financial completion still requires human KYC, gas credits, a funded balance and owner-executed transactions.
