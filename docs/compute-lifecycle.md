# Agent compute and persistence

Ordinary chat runs on the application backend and account storage. Opening the app does not start a VM or allocate a separate container service. The browser makes a zero-compute status request so the UI can show that the agent is ready. A compute lease is created only when the agent actually needs shell, code, browser, or full-computer work.

Shell and code run in a hardened worker container inside the user's per-user Azure VM. The VM is the outer security boundary; the worker container has a read-only root, no capabilities, no network, resource limits, and only the task workspace mounted read/write. Browser and computer tools continue to run under the protected browser account in the VM, outside the worker container. The image is cached on the VM, so a warm VM starts a tool container without a second cloud compute allocation. `AZURE_WORKER_IMAGE` may point to a pinned pre-built image; the bootstrap builds the default image once if it is missing.

Browser navigation, shell commands, and code execution still acquire a per-user VM lease only when the agent calls one of those tools. A status read never provisions a missing VM. The VM remains warm for `AZURE_VM_IDLE_MINUTES` (default 10) after the last lease, then the existing sweeper deallocates it. An active lease prevents deallocation. The retired `/api/sandbox/lease` browser endpoint returns 410 so simply opening the app cannot start a VM.

Canvas browser/computer viewing uses a persistent Chromium CDP screencast relay. Chromium stays open on the VM and sends binary live frames over one authenticated outbound WebSocket; Canvas sends pointer and keyboard events back on the same authenticated socket. There is no VNC/RDP port and no screenshot-per-action loop. The private Blob screenshot path remains only as a compatibility fallback when the public relay origin is not configured.

Memory, agent documents, mailbox, Shop Pay records, chats, and task state live in the account backend, independent of compute. The agent browser tool uses one private Chromium profile per user VM, with a separate tab for each active task. Website cookies, including session cookies, are saved in an owner-only file inside that profile so sign-ins can survive a browser restart. Passwords and API keys remain in the encrypted account vault, and Chromium's password manager is disabled. With `AZURE_DURABLE_STATE` enabled (the default), the VM archives `/home/lingon/workspace`, `/var/lib/lingon-browser/sessions`, and `/home/lingon-desktop` to a private Azure Blob container after the last session and before VM deallocation, then restores them when a replacement VM starts. The backup must report success before deallocation proceeds. The VM OS disk also survives normal deallocation. Browser caches and desktop runtime/cache folders are excluded from the archive; temporary worker files and arbitrary OS paths outside those three directories are not covered by replacement-VM restore. The worker container filesystem is ephemeral and must never be treated as the source of truth; its mounted workspace is the durable working copy.

The optional external Container Apps presence pool is disabled by default and is not part of the normal production path. It can be enabled only by setting `AZURE_CONTAINER_SESSION_PRESENCE=external` and `AZURE_CONTAINER_SESSION_ALLOW_BILLING=true`, plus the endpoint and identity configuration. It is useful for a separate burst workload, but it does not improve ordinary chat and should not be enabled just to make the agent appear online. Configure `AZURE_DURABLE_STATE=true` for private workspace backup, set `AZURE_WORKER_IMAGE` to a pinned image or use the built-in bootstrap image, apply every Supabase migration in filename order (including `20260921203000_vm_idle_grace.sql`), and run the live VM restore check before opening production traffic.

The normal path has one **workspace compute** meter: the per-user VM while it is running. The worker container consumes that VM's CPU and memory and does not create a second Container Apps charge. Model/API tokens, managed disks, storage, networking, image storage, and Blob snapshots can still incur separate charges. Azure's deallocated state releases VM compute billing.

Check `/api/sandbox/presence` for account-only readiness and `/api/sandbox/status` separately for VM state. A normal app load should not change VM power; a browser/shell/code tool should start the VM on demand, restore state, start the worker container when needed, back up state when work ends, and deallocate the VM after the idle grace. An active background task keeps its lease even when the app is closed. A production failover test should create a file and browser cookie, finish the session, replace the VM, and verify both restore. Automated tests cover routing, lease grace, identity isolation, container command construction, and UI lifecycle; they cannot replace that live infrastructure test.
