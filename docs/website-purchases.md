# Website purchases in the agent VM

The agent can prepare a merchant checkout in its account-scoped VM browser. The final `browser_submit` action requires a fresh owner decision. A purchase approval shows the HTTPS website, line items, total and currency, delivery address, and the payment method as the checkout shows it. The server binds the decision to the current page URL, visible checkout text and form elements, action target, and payment method. If the page changes, execution stops for a new review.

Belna never stores card details, not even masked metadata. To pay, the agent signs in to the merchant with the owner's saved website login and selects either **Shop Pay** or a card the owner already saved in that **merchant account**. The merchant keeps the card and only ever displays it masked (for example "Visa ending in 1234"). `browser_submit` takes `payment: { method: 'shop_pay' | 'saved_card', label }`; the label must be visible on the live checkout and may not contain a card number. Card numbers, CVC and identity codes are rejected by the agent vault and fill tools. If a merchant has no saved card or Shop Pay, the agent stops and asks the owner to add one in their own merchant account.

For BankID, passkeys, one-time codes and card-issuer checks, `browser_auth_handoff` pauses the agent and gives the owner control of the live VM browser. The owner checks the merchant and the request in their own identity app, completes the challenge, then resumes the agent. The app does not act as a BankID relying party; each merchant handles its own BankID transaction. The agent receives no PIN or challenge response.

`supabase/migrations/20260925150000_drop_merchant_payment_methods.sql` removes the earlier masked-card table. Browser handoff requires the existing live Azure VM relay and a configured `LINGON_PUBLIC_ORIGIN`. The generic edge VM path supports the structured purchase approval but does not expose the live handoff; deploy the Node live-browser host for BankID and similar challenges.

Relevant PCI guidance: [PCI SSC FAQ 1574](https://www.pcisecuritystandards.org/faqs/1574/) says software and service-provider vaults must not retain card verification codes for future transactions, even with cardholder permission.
